## Resolving CONTEXT.md gray areas 3 and 4 (planner decision, not user-decided)

`01-CONTEXT.md`'s `<deferred>` block leaves two questions open and instructs the planner to resolve
them from FLOW-01 and FLOW-05. Here is the resolution, stated in full so it can be rejected cheaply
now rather than discovered in Phase 3.

### Gray area 3 — the discriminated-union shape

```
export type BridgeStepId     = 'approve' | 'submit' | 'relay'
export type BridgeStepStatus = 'idle' | 'pending' | 'processing' | 'confirmed'

export interface BridgeStep { id: BridgeStepId; status: BridgeStepStatus }
export type BridgeSteps = readonly [BridgeStep, BridgeStep, BridgeStep]

export type BridgeBlockedReason =
  | 'disconnected' | 'undeployed' | 'wrong-chain' | 'switching-chain'
  | 'invalid-amount' | 'invalid-recipient'

export type BridgeFlowState =
  | { phase: 'blocked';    reason: BridgeBlockedReason; steps: BridgeSteps }
  | { phase: 'ready';      steps: BridgeSteps }
  | { phase: 'approving';  steps: BridgeSteps }
  | { phase: 'submitting'; steps: BridgeSteps }
  | { phase: 'relaying';   steps: BridgeSteps }
  | { phase: 'done';       steps: BridgeSteps }
  | { phase: 'failed';     failure: DecodedBridgeError; failedStep: BridgeStepId; steps: BridgeSteps }
```

`phase` is the discriminant the action button reads (BTN-01); `steps` is what the stepper reads
(STEP-01..STEP-03). **Both live on every variant of one value** — that is FLOW-01 made concrete.
Neither the label/variant/icon copy nor the per-step status text lives here: STEP-03's three status
sentences and the button's labels are presentational and belong to Phase 3, which maps
`phase`/`status` to copy. This function carries semantics only.

`BridgeBlockedReason`'s six members mirror `getActionState()`'s six leading guards one-for-one, which
is what makes FLOW-03's deletion of that function a deletion rather than a partial migration.

### Gray area 4 — how failure relates to the three steps

`PROJECT.md` records the deliberate decision that failures render in **one shared error banner**, not
a per-step failed state, with per-step failure deferred to v2-01. So there is deliberately **no
`'failed'` member of `BridgeStepStatus`**. Instead:

- `phase: 'failed'` carries the `DecodedBridgeError` itself, so the banner reads the same single value
  the stepper does — no second channel.
- `failedStep` records which step was in flight, preserving the provenance the banner needs (and
  which v2-01 will later use for a per-step visual) without introducing a per-step failed status now.
- **The FLOW-05 invariant:** in the `failed` variant, every step whose status would have been
  `pending` or `processing` is returned as `idle`. Steps already `confirmed` stay `confirmed`. That is
  precisely "the flow leaves the pending state, so no step is ever left spinning".

### Precedence order (guard clauses, most-blocking first)

1. `failure` present → `failed`
2. `!isConnected` → `blocked` / `disconnected`
3. `!isDeployed` → `blocked` / `undeployed`
4. `!isCorrectChain` → `blocked` / `switching-chain` when `isSwitchingChain`, else `wrong-chain`
5. `!hasValidAmount` → `blocked` / `invalid-amount`
6. `!hasValidRecipient` → `blocked` / `invalid-recipient`
7. `relay.isFinalized` → `done`
8. `relay.isInitiated` → `relaying`
9. `bridge.isPrompting || bridge.isConfirming` → `submitting`
10. `approve.isPrompting || approve.isConfirming` → `approving`
11. otherwise → `ready`

**Failure first is deliberate.** FLOW-05's whole point is that a failure must be visible and must stop
the spinners; a wallet disconnect or a chain switch occurring after a failure must not hide the
explanation. The consequence — that a failure is sticky until the caller clears it — is Phase 3's
responsibility and is recorded in `<carried_constraints>` below.

*Reversibility: `costly`. `BridgeFlowState` is consumed by Phase 2's relay-status hook and by all
three Phase 3 plans (orchestration hook, stepper, action button). Changing the variant set or the
discriminant later is a coordinated cross-module change. It is NOT `one-way`: nothing persists this
shape — FLOW-04 rehydrates raw inputs (message id and transaction hashes), never the derived output,
so there is no migration and no published contract. No `checkpoint:decision` is therefore inserted.*
