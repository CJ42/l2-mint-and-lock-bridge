<assumption_delta_decision>
## Assumption-Delta Architecture Checkpoint — recorded verdict

**Detector signals, judged against real phase scope:**

- `pluralization` on `"fallback"` (`"…→ generic fallback)"`) — **false positive.** "Generic fallback"
  is the terminal branch of a single ordered decode chain, not a second platform / tenant / source
  of truth. Nothing was pluralized.
- `chosen` on `"custom"` (`"…every Errors.sol custom error…"`) — **false positive.** "Custom error"
  is Solidity vocabulary for a typed revert. No constant became a parameter.

**But inspecting the real scope surfaced a genuine generalization the signals only gestured at.**
The phase's decode chain is an ordered set of ten decoders sharing one return type. The shape both
`.planning/research/STACK.md` (its `mapBridgeError` sketch returns a bare `string`) and
`01-PATTERNS.md` (`{ message: string; errorName?: string }`) imply keeps **the message string
primary**. Under that model "which decoder fired" is unrecoverable downstream: Phase 3's banner,
the exhaustiveness tests, and any future extension would have to re-string-match the very text the
module just produced, and ERR-09's "extensible" stays aspirational.

- **Primary noun (now):** the **decoded bridge-error outcome, tagged by the decoder that produced
  it** — `DecodedBridgeError.kind`.
- **Decision: `promote`.** `kind` is promoted to primary and made the discriminant; `message` is
  demoted to a *rendering* of the tagged outcome. This is a promote, not an add-alongside: there is
  no path that returns a bare string with `kind` bolted on beside it, and no branch may return
  without a `kind`.
- **Rationale:** a later decoder that does not fit the string-primary model (one carrying structured
  evidence, or one Phase 3 must branch on) can be *stored* under add-alongside but never *acted on*.
  Promoting now costs one type declaration; promoting later costs every call site.

**Companion invariant test: ACCEPTED.** Planned as Task 3 of Plan 01-02 — every one of the ten
`kind` values is reachable from a fixture, every fixture maps to exactly one `kind`, the chain is
total (no input yields `undefined` or throws), and `unknown` is the only branch reachable for an
unrecognised selector. That test goes red the instant a future phase reintroduces a string-primary
return or drops a branch.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `contracts/out/*.json` → codegen → `ui/src/lib/generated.ts` | Build-time file read. The ABI the UI decodes every revert against originates from files on local disk written by an external toolchain. |
| chain node → viem error object → `decodeBridgeError` → user-facing string | Revert data is attacker-influenceable bytes. Any address can craft a call that reverts with arbitrary payload; that payload reaches user-visible copy. |
| lockfile / `node_modules` → `ui` workspace | A dependency declaration is added to `ui/package.json`, requiring `bun install`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | `wagmi generate` reading `contracts/out/` | medium | mitigate | `forge: { build: true }` forces a rebuild from `contracts/src/` on every run rather than trusting whatever is already in `out/` (note: `out/` currently holds a stale `WrappedUSDC.sol` artifact from a removed source file, proving stale artifacts do persist). The narrow four-entry `include` excludes it. Task 1's test asserts the exact 21-name error set, so a tampered or truncated artifact fails the build rather than silently degrading every decode to the generic branch. |
| T-01-02 | Information disclosure | raw revert hex + decoded `args` interpolated into `DecodedBridgeError.message` | high | mitigate | The decode layer returns **plain strings only** — never markup, never HTML. Raw revert data is normalised to lowercase `0x`-prefixed hex before interpolation, so no non-hex byte from the payload can reach the message. Recorded as a constraint on Phase 3: the error banner must render this string as a React text child (auto-escaped) and never via `dangerouslySetInnerHTML`. |
| T-01-03 | Denial of service | unbounded revert payload inflating the message | low | mitigate | Raw hex bounded to the 4-byte selector plus at most 64 further hex characters with an ellipsis (Task 1). Plan 01-02 extends the same bound to the `Error(string)` reason path. |
| T-01-04 | Spoofing | a decoded message that names a cause the decoder did not actually read | medium | mitigate | The `promote` decision (see `<assumption_delta_decision>`) makes provenance a first-class `kind` field rather than an inference from message text, and `must_haves.prohibitions` forbids presenting a guessed cause as decoded evidence. Plan 01-02 Task 3's exhaustiveness test enforces one fixture → exactly one `kind`. |
| T-01-SC | Tampering | `bun install` after adding `@types/bun` to `ui/devDependencies` | low | accept | This is not a package acquisition. `@types/bun@1.3.14` is already declared by `relayer/package.json`, already resolved in `bun.lock`, and already materialised at `node_modules/.bun/@types+bun@1.3.14` — verified by direct inspection. Bun's isolated linker simply does not symlink it into `ui/` until `ui` declares it; the install introduces no new package name and no new version into the dependency tree. No new external package is added anywhere in this phase. Accordingly no blocking legitimacy checkpoint is inserted, and no `## Package Legitimacy Audit` is required. If the developer disagrees with this reading, the correct override is to add a `checkpoint:human-verify` before Task 1's install step. |
