# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This contract governs three new/changed surfaces in `ui/src/`: the hand-built `Stepper`
(`stepper.tsx`), the hand-built `ActionButton` (`action-button.tsx`), and the single error
banner replacing three scattered `<p className={styles.error}>` blocks in `bridge-card.tsx`
(lines 345–351). It does not touch `message-explorer.tsx` (Phase 2 territory) or the hero
title/subtitle/facts markup (unchanged, only extended with the stepper mount point).

Overrides in force, matching PROJECT.md / 03-CONTEXT.md precedent (recorded, not silent):
**shadcn/ui is explicitly not used** — the reference pattern in `TX_FLOW.md` (`Button`,
`Spinner` imported from `@/components/ui/*`) is reimplemented as hand-built CSS Module
components (`ActionButton`, `Spinner`) importing from `@/components/*` directly.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn explicitly rejected (PROJECT.md Key Decisions); `components.json` confirmed absent |
| Preset | not applicable |
| Component library | none — hand-built CSS Modules, co-located `component-name.module.css` |
| Icon library | none — hand-drawn inline SVG, 16×16 `viewBox`, `stroke="currentColor"`, `strokeWidth="1.4"`, `strokeLinecap`/`strokeLinejoin="round"`, `aria-hidden="true"` — matches the existing `SwapIcon()` in `bridge-card.tsx` exactly; new icons (wallet, retry, checkmark) follow the same convention |
| Font | IBM Plex Mono (`--font-plex`, already loaded via `next/font/google` with weights 400/500/600/700); this phase uses only 400 and 600 |

New shared component this phase must introduce: `ui/src/components/spinner.tsx` +
`spinner.module.css` — a single animated ring glyph (CSS `@keyframes` rotation, no JS), consumed
by both the stepper (blue-on-white) and the action button (white-on-blue). One component, two
color props — not two separate hand-rolled spinners.

## Spacing Scale

Declared values (must be multiples of 4) — governs the **new** elements this phase adds
(stepper, action-button internals, error banner). Pre-existing `bridge-card.tsx`/`page.tsx`
spacing (26px card padding, 18–22px field gaps, etc.) predates this phase and is not touched.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Step label-to-caption gap; badge internal padding-y |
| sm | 8px | Step circle-to-text gap; button icon/spinner-to-label gap; badge padding-x |
| md | 16px | Error banner padding; gap between stepper and hero facts block |
| lg | 24px | Vertical gap between stepper steps (row rhythm) |
| — | 24px | Step circle diameter (fixed across all three step states — see Stepper Visual States) |
| — | 48px | Action button min-height (existing `.action`, unchanged, already a multiple of 8) |

Exceptions: step circle diameter (24px) and connector line width (2px) are fixed decorative
constants, not spacing rhythm — declared here for completeness, not counted against the scale.
No 44px touch-target exception is needed: step circles are non-interactive (display only, no
click handler); the action button's existing 48px min-height already clears the touch-target bar.

## Color

The app already carries three pre-existing accent-adjacent colors (blue = primary interactive,
orange = brand mark + advisory notices, danger-red = errors) rather than a clean single 10%
accent — that is inherited, not introduced here. This phase adds exactly **one** new semantic
color, tightly scoped, because STEP-02 mandates a green checkmark that has no existing token:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--white` `#ffffff` | Page background, card background, input fields |
| Secondary (30%) | `--surface` `#fafafb` / `--border` `#e3e3e8` | Chain panels, card borders, upcoming-step circle border |
| Accent — primary (10%) | `--blue` `#181ea9` | CTA button fill, links, focus rings, pending-step spinner, `.tag`, `.self` button |
| Accent — brand/advisory (pre-existing) | `--orange` `#e5673f` | Title punctuation dot, "Bridge undeployed" notice, message-explorer "live" dot — **not extended by this phase** |
| **New — success (this phase)** | `--green` `#1f9254` (add `--green-soft: rgb(31 146 84 / 10%)`, `--green-line: rgb(31 146 84 / 24%)` to `globals.css`, mirroring the existing `--blue-soft`/`--blue-line` naming pattern) | **Reserved exclusively for confirmed/success signals: step-confirmed circle fill + checkmark, the "Done ✓ — view on explorer" button's `success` variant border/accent, and nothing else** — never used for any other interactive or informational element |
| Destructive | `--danger` `#c8102e` (add `--danger-soft: rgb(200 16 46 / 10%)` to `globals.css`, mirroring `--orange-soft`) | Error banner headline + left-border accent, field-level validation errors (existing `.error`) — never used for button chrome, even on the `failed` flow state (the button stays primary/blue; the banner alone carries the danger signal) |

Accent reserved for: **blue** — the action button in every non-terminal state, all links, focus
rings, the pending-step spinner and its circle border. **green** — step-confirmed circles/checks
and the completed-state button only. **orange** — unchanged pre-existing usage (title dot,
undeployed notice, explorer live dot), not touched or extended by this phase. **danger-red** —
error banner and field validation only, never the button.

## Stepper — Visual States (STEP-01 / STEP-02 / STEP-03 / STEP-04 / D-07 / FLOW-05)

Three steps, always visible (D-07), fixed order: **Bridge Approved → Bridge tx submitted →
Bridge tx relayed**. Mounted in `page.tsx`'s `styles.hero` column, directly after `.facts`
(STEP-01), with `margin-top: 16px` relative to the facts list.

### The three per-step states

Every step circle is a **fixed 24px diameter** in all three states — this is a hard constraint,
not a suggestion: STEP-02 only names two states (pending/confirmed) but D-07 requires an
always-visible stepper with **no layout shift** as steps advance, so the third state (`upcoming`,
introduced by this contract) must occupy identical space.

| State | Circle | Glyph | Label color | Caption shown? | Caption color |
|---|---|---|---|---|---|
| **upcoming** (new — this contract's answer to the open question) | 24px, `1.5px solid var(--border)`, background `var(--white)` | step index digit (`1`/`2`/`3`), 11px/600, `var(--muted)` | `var(--muted)` | **no** — showing nothing is the honest choice; inventing placeholder copy (e.g. "Not started") would be the first faked-state STEP-03 does not ask for | — |
| **pending** (STEP-02 blue spinner) | 24px, `1.5px solid var(--blue-line)`, background `var(--white)` | `<Spinner>` (blue-on-white, 16px) | `var(--ink)` | yes | `var(--muted)`, 11px |
| **confirmed** (STEP-02 green checkmark) | 24px, filled `var(--green)`, no border | white checkmark glyph, 12px | `var(--ink)` | yes | `var(--muted)`, 11px |

Connector line between two circles: 2px wide, `var(--green)` if the step **above** it is
confirmed, else `var(--border)`. This is a real-state trail, not a progress bar — it only ever
reflects a transition that has actually completed (no faked interpolation), consistent with the
no-faked-states constraint.

### STEP-03 copy mapping — which of the three TX_FLOW.md sentences each step shows

TX_FLOW.md defines exactly three sentences (pending / processing / confirmed), written for a
single wallet-driven transaction with two distinct in-flight phases. Steps 1 and 2 are each one
wallet transaction and map cleanly to all three; step 3 has no wallet interaction and only one
in-flight phase, so it uses one of the two "in-flight" sentences, not both — this is the
resolution the additional-context flagged as needed.

| Step | Pending caption (wallet prompt open) | Processing caption (receipt awaited) | Confirmed caption |
|---|---|---|---|
| 1. Bridge Approved | *"Your transaction is being submitted to the network…"* | *"Your transaction has been picked up and is being processed…"* | *"Your transaction has completed successfully!"* |
| 2. Bridge tx submitted | *"Your transaction is being submitted to the network…"* (also covers the brief D-01 simulate-then-open-wallet gap between step 1 confirming and this wallet prompt opening — no separate "simulating" copy is invented) | *"Your transaction has been picked up and is being processed…"* | *"Your transaction has completed successfully!"* |
| 3. Bridge tx relayed | — (no wallet interaction) | *"Your transaction has been picked up and is being processed…"* — the **only** caption this step ever shows while active, for the entire relay-watch window (there is no separate "processing" sub-phase to distinguish it from) | *"Your transaction has completed successfully!"* |

### Failure presentation (FLOW-05 — the subtlest question in this phase)

PROJECT.md rules out a per-step failed state (V2-01, deferred) and mandates one shared error
banner. The rendering rule that satisfies both FLOW-05 ("leaves pending, nothing left spinning")
and that constraint simultaneously:

**On `failed`, any step whose derived per-step status is not literally `confirmed` renders as
`upcoming` — reverting from `pending` back to its neutral, honest starting state. Steps already
`confirmed` at the moment of failure keep their green checkmark (that transaction really did
succeed — reverting it would be dishonest, not neutral).** No step ever renders red, gets a
special "failed" glyph, or gets a shaking/error animation. 100% of the failure explanation lives
in the error banner; the stepper's only job during a failure is to stop claiming something is
still in flight.

Example: bridge write reverts after approve already confirmed → step 1 stays green-checked, step
2 reverts from its spinner to the neutral `upcoming` circle, step 3 stays `upcoming` (it was
already there) — and the error banner explains why, with the button offering `Try again`.

### Refresh-recovery rendering (FLOW-04, visual half only — persistence mechanics are the hook's concern)

On mount, before rehydration resolves, the stepper renders in its `upcoming` state for all three
steps — this is not a separate loading skeleton, `upcoming` already IS the correct "we don't know
yet" visual (it claims nothing). Once rehydration resolves (from persisted storage, backstopped
by a bounded chain scan per Pitfall 7), the stepper repaints once to the real restored state. No
intermediate "restoring…" spinner state is introduced — that would be a state STEP-02/03 never
defined and risks becoming a fourth faked phase.

## Transport Health Visibility (Phase 2 D-07's deferred call — resolved here)

The tension on record: the milestone's core value is "never left guessing," but an always-on
connection indicator is chrome noise on a portfolio demo. Resolution — **render only when
degraded, and only where it is load-bearing**:

- **Scope:** this contract governs only the flow's own stepper (step 3, "Bridge tx relayed" —
  the one step actually driven by `use-relay-status.ts`'s live watch). The message explorer's own
  live/staleness indicator is Phase 2/LIVE-09 territory and is not extended by this phase.
- **When `transportMode === 'connected'` (or the value has not yet resolved on first mount):
  render nothing.** Absence is the signal for "healthy" — this is deliberate, not an oversight:
  showing a permanent "connected" badge is exactly the chrome-noise outcome CONTEXT.md's tension
  note warns against, and treating "not yet resolved" the same as "connected" avoids a
  first-paint flash of a false "reconnecting" badge before the watchdog has classified anything.
- **When `transportMode` is `stale` or `reconnecting`: show a small pill directly under step 3's
  caption** (only while step 3 is the active/pending step — a user is only watching for relay
  liveness during that window): `Reconnecting…`, `--orange` text on `--orange-soft` background,
  10px/600, `4px 8px` padding, matching the existing `.tag`/`.pending` badge treatment.
- **When `transportMode === 'polling-fallback'`: show the same pill in a calmer tone** —
  `Live updates via polling`, `--muted` text on `--surface` background — because polling-fallback
  is a working degraded mode, not an alarm; it should read as "still honest," not "something is
  wrong."
- This satisfies the core-value tension without new chrome: the ONE moment transport health
  actually matters to the user (waiting on the relay step) is the only moment it can appear.
