<objective>
Ship the phase's end-to-end path: one click in the bridge card runs the whole approve → simulate →
bridge → receipt sequence inside a new `use-bridge-flow.ts` hook, and the action button's label,
variant, icon and disabled state are read off the single `BridgeFlowState` that sequence produces.

Purpose: this is the architecture proof for the whole phase. Every later plan hangs a second consumer
(the stepper) or a second input source (persisted storage) off contracts this plan establishes, so if
the single-derived-state model is wrong it must be wrong here — after one commit — not after the
stepper and the persistence layer have already been built on top of it. It is also where the phase's
irreversible deletion happens: the ten-branch action-state helper and the duplicated hash state leave
`bridge-card.tsx` for good.

Output: `ui/src/hooks/use-bridge-flow.ts`, `ui/src/components/action-button.tsx` +
`action-button.module.css`, `ui/src/components/spinner.tsx` + `spinner.module.css`, the new colour
tokens in `globals.css`, and refactored `bridge-card.tsx` / `bridge-card.module.css` / `page.tsx`.
</objective>

<assumption_delta_decision>
## Assumption-Delta Architecture Checkpoint — recorded verdict

**Detector signal, judged on merits.** The scan fired one `pluralization` signal on the term
`"second"`, matched inside the ROADMAP phrase *"with no second derivation"*. That is a **false
positive on its face** — the phrase is a prohibition against plurality, not evidence of it.

**But the real transition the signal gestured at is genuine, and runs the other way.** Before this
phase, `bridge-card.tsx` is the sole owner of the bridge's input and transaction state
(`directionKey`, `amountInput`, `recipientInput`, and the two transaction hashes are card-local
`useState`), and it derives its own button state from raw flags. After this phase, that state has a
second and more authoritative claimant: `use-bridge-flow.ts`, called from `page.tsx`, because
STEP-01 puts a second consumer (the stepper) in the hero column where card-local state is
unreachable.

- **Primary noun (now):** the bridge flow's combined input-and-transaction state, owned by
  `use-bridge-flow.ts` and expressed as one `BridgeFlowState` plus its input setters.
- **Decision: `promote`.** The hook's state is promoted to primary and the card's local `useState`
  for those fields is **removed**, not kept alongside. Add-alongside here is not merely untidy — it
  is precisely the drift FLOW-01 and BTN-01 exist to forbid, and the drift the deleted ten-branch
  helper already demonstrated in production.
- **Rationale:** two owners of the same fact means a stepper in the hero column and a button in the
  card can disagree about which step is in flight, and nothing in the type system would notice. One
  owner makes that disagreement unrepresentable.

**Companion invariant: ACCEPTED, as acceptance criteria rather than a new test file.** The project
has no React rendering test harness (Phase 1 and Phase 2 test pure modules with `bun test`), so
adding one is out of scope. Instead Task 2 asserts structurally that `bridge-card.tsx` and
`action-button.tsx` contain no `useState` for the promoted fields and no branch reading a raw
progress flag — a check that goes red the instant a future change reintroduces the singular
card-local assumption.
</assumption_delta_decision>

<planner_flagged_decisions>
Decisions the planner made on the developer's behalf. Each is recorded so it can be overridden
cheaply now rather than discovered later.

1. **The hook exposes one flat result object, not a grouped sub-object per concern.**
   `03-CONTEXT.md` leaves "how much of the hook result `BridgeCard` receives as props versus one
   grouped object" to Claude's discretion. Chose a flat object matching the
   `UseBridgeMessagesResult { messages, isLoading, error, refresh }` convention already in the
   codebase, spread into `BridgeCard` as individual props. *Reversibility: reversible.*

2. **`simulateContract` / `writeContract` / `waitForTransactionReceipt` come from `wagmi/actions`,
   obtained with `useConfig()`.** `03-CONTEXT.md` leaves the entry point to discretion;
   `03-RESEARCH.md` verified by direct filesystem read that `wagmi/actions` re-exports
   `@wagmi/core/actions` wholesale, so no new dependency enters `ui/package.json`. Chose it over a
   module-level viem client because the write path must go through the user's connected wallet, which
   is what the wagmi `Config` carries. *Reversibility: reversible.*

3. **The `approve` transaction gets no pre-flight simulation.** SIM-01 mandates simulation only for
   the bridge transaction; a well-formed ERC20 `approve` essentially cannot revert, and its real
   failure mode — insufficient native gas — is already covered by Phase 1's insufficient-gas decode
   branch. This matches the leaning recorded in `03-CONTEXT.md`'s Claude's Discretion block.
   *Reversibility: reversible.*

4. **`DecodeBridgeErrorInput.gasEstimate` is passed as undefined throughout this phase.**
   `simulateContract` performs `eth_call`, not `eth_estimateGas`, so no gas figure falls out of the
   sequence naturally, and Phase 1's shortfall helper already carries two further fallback sources.
   Spending an extra RPC round-trip to sharpen a message on a path Phase 1 already handles is not
   worth it. *Reversibility: reversible.*

5. **The insufficient-balance check stays a field-level error on the amount input, not a flow
   failure.** Phase 1's locked `BridgeBlockedReason` has no member for it and the UI-SPEC's
   fourteen-row button table has no row for it, so routing it through the flow state would require
   changing a Phase 1 contract. `03-CONTEXT.md` scopes the single-banner replacement to the three
   transaction-error paragraphs only and explicitly keeps the existing recipient field error, so an
   `amountError` sibling is the consistent home. Today's behaviour is preserved exactly: the button
   is enabled, and clicking with an over-balance amount surfaces the field error and sends nothing.
   *Reversibility: reversible.*

6. **`page.tsx` stops holding `activeMessageId` in local state; the explorer reads the hook's
   `messageId`.** With the flow hook owning the messageId, a page-local copy would be the second
   owner this phase exists to remove. `MessageExplorer` keeps its existing four-field props
   contract; only the source of `activeMessageId` changes. *Reversibility: reversible.*

**No decision in this plan is `one-way`.** None requires a data migration, breaks a published
contract, or cannot be undone. `REVERSIBILITY_GATES=true` therefore inserts no `checkpoint:decision`
here and `autonomous` stays `true`. Stating that explicitly rather than manufacturing a gate. The one
`costly` decision (D-05) was made by the developer in the discussion session, so the door is already
walked through and re-asking would be checkpoint fatigue.
</planner_flagged_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → origin-chain public RPC | Every simulate, write and receipt result originates from unauthenticated third-party infrastructure that can lie about chain state. |
| chain → error banner | Decoded revert bytes are attacker-influenceable: any address can deploy a contract that reverts with chosen data, and the bridge's own errors carry caller-supplied evidence values. |
| user gesture → wallet extension | D-02 opens the second wallet prompt programmatically, after an await, from a sequence the user's own click started — a user-activation boundary browsers and wallets police. |
| hook → presentational components | `action-button.tsx` renders whatever the hook's derived state says and makes no independent check, so any false claim in the hook reaches the user unfiltered. |
