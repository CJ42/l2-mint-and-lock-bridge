<objective>
Make a mid-bridge page reload survivable: persist a minimal record of the in-flight flow, and on the
next mount restore the form and re-derive the step position from chain state rather than from the
record's own claims.

Purpose: this is the scenario `.planning/research/PITFALLS.md` Pitfall 7 flags as one a reviewer is
likely to hit deliberately — refreshing the page to check the flow is real. Without persistence every
`useState` is lost on reload and the stepper resets to step one with no memory of a transaction that
is still mining. The design's load-bearing half is not the record; it is the refusal to trust it: a
restored message id goes to the relay watch's own bounded seed scan, and a restored hash goes to a
receipt lookup, so what the user sees after a reload is what the chain says, not what the browser
remembered.

Output: `ui/src/lib/flow-storage.ts` with tests, and the persistence and rehydration wiring inside
`ui/src/hooks/use-bridge-flow.ts`.
</objective>

## Contract this plan establishes

**`ui/src/lib/flow-storage.ts`** — named exports only, object parameters, explicit return types,
matching every other module under `ui/src/lib/`:

```typescript
export const PERSISTED_FLOW_VERSION = 1

export interface PersistedFlow {
  version: typeof PERSISTED_FLOW_VERSION
  address: Address
  directionKey: 'baseToArbitrum' | 'arbitrumToBase'
  amountInput: string          // the raw decimal string, never a parsed bigint
  recipientInput: string
  approveHash?: Hex
  bridgeHash?: Hex
  messageId?: Hex
  updatedAt: number
}

export type FlowStorageBackend = Pick<Storage, 'getItem' | 'setItem' | 'removeItem'>

export function persistedFlowKey({ address }: { address: Address }): string
export function readPersistedFlow(
  { address, backend }: { address: Address; backend?: FlowStorageBackend },
): PersistedFlow | undefined
export function writePersistedFlow(
  { record, backend }: { record: PersistedFlow; backend?: FlowStorageBackend },
): void
export function clearPersistedFlow(
  { address, backend }: { address: Address; backend?: FlowStorageBackend },
): void
```

There is deliberately **no** `relayed`, `finalized`, `isDone` or `stepPosition` field. Every one of
those would be a claim the hook could trust instead of re-checking, which is exactly the failure this
design exists to prevent. The step position is reconstructed from the three optional hashes and ids
plus a chain lookup, never read back as a stored fact.

<decisions_recorded>
This plan resolves the first of the two gray areas `03-CONTEXT.md`'s `<deferred>` block left open and
handed to the researcher and planner: refresh-recovery mechanics. `03-CONTEXT.md` records no D-number
for it, so the resolution below is the planner's, grounded in `.planning/research/PITFALLS.md`
Pitfall 7 and `03-RESEARCH.md` Architecture Patterns Pattern 4, and recorded so it can be rejected
cheaply now.

- **What is persisted:** a whole flow record — direction, the two raw input strings, and whichever of
  the approve hash, bridge hash and message id exist — rather than the message-id pointer alone.
  Pitfall 7 recommends the pointer with a chain scan as backstop; the pointer alone is insufficient
  here because it only exists after the bridge receipt mines, so a reload during the approve or the
  bridge prompt would still lose everything, which is the middle of the window FLOW-04 names.
- **Where:** the browser's persistent local store, not the per-tab one. Pitfall 7 explicitly names
  "the reviewer refreshes the page to check it's real" as the likely demo scenario, and that includes
  closing and reopening the tab, which clears per-tab storage.
- **Keyed:** per connected wallet address, so switching accounts cannot restore another account's flow.
- **Cleared:** on done, on failed, and on a direction flip — deleted rather than marked complete,
  because D-08 already keeps the *rendered* terminal state visible from in-memory state, so a stale
  terminal record survives only to be misread on a later visit.
- **Trusted?** No. On rehydration the record supplies inputs and hashes; every confirmation is
  re-derived from chain state. See the prohibitions in `must_haves`.

*Reversibility: `reversible`, and deliberately made so. A persisted format is the usual one-way door
— but this record carries an explicit schema version and the reader discards anything it does not
recognise, falling back to idle. There is therefore no migration to write and no stored state a later
change could strand, which is why this plan removes the irreversibility rather than gating it with a
`checkpoint:decision`.*

- **D-08, extended to storage.** The reset that clears in-memory progress on a direction flip or a new
  submission also clears the record; an incidental input edit clears neither.
- **Phase 1's carried constraint honoured.** Phase 1 records that `failure` outranks every other guard
  and that Phase 3 must clear it when a fresh attempt begins. Rehydration never restores a failure —
  a failed run's record is deleted at the moment it fails, so there is nothing to restore.

**No decision in this plan is `one-way`.** `REVERSIBILITY_GATES=true` therefore inserts no
`checkpoint:decision` and `autonomous` stays `true`.
</decisions_recorded>

<planner_flagged_decisions>
1. **The record carries an explicit schema version and the reader rejects any other value.**
   `03-RESEARCH.md`'s Pattern 4 shape has no version field and flags the whole shape `[ASSUMED]`.
   Adding the version is what converts a persisted format — normally the archetypal one-way door —
   into a reversible decision: a future change bumps the constant and every older record is discarded
   on read with no migration. *Reversibility: reversible, and it is what makes the rest of this plan
   reversible too.*

2. **The storage backend is an injectable parameter defaulting to the browser store.**
   `03-RESEARCH.md`'s Don't Hand-Roll table warns against scattering environment guards through the
   hook. Making the backend a parameter puts the availability guard in exactly one place, keeps the
   hook free of any direct browser-storage call, and lets `bun test` prove the module against a fake
   backend without a browser environment — which matters because every other test in this project is
   a pure-module `bun test` and there is no DOM harness to add one to. *Reversibility: reversible.*

3. **`updatedAt` is recorded but no expiry logic reads it.** An age-based discard would be a
   behaviour nobody asked for, and a wrong threshold would silently drop a genuinely in-flight
   transaction — the exact failure FLOW-04 exists to fix. It is written as a diagnostic a later phase
   could use. *Reversibility: reversible.*

4. **Rehydration restores the form unconditionally but the step position only as far as the chain
   confirms it.** The two halves are deliberately asymmetric: a blanked form is pure loss with no
   correctness risk, whereas a restored step position is a claim, so it must be earned from a receipt
   or from the relay watch's own seed scan. *Reversibility: reversible.*

5. **A restored approve-confirmed state does not auto-resume the bridge leg.** D-02's one-click model
   opens the second prompt inside the sequence the user's own click started; re-opening a wallet
   prompt from a mount effect is precisely the user-activation risk D-02's own fallback note warns
   about, and it would mean a page reload could trigger a signature request. The restored state is
   approve-confirmed and clickable. *Reversibility: reversible.*
</planner_flagged_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser store → hook | The stored record is same-origin-writable: any script on the origin, and any browser extension with access, can rewrite it. Everything the hook reads back is untrusted input. |
| stored hash → origin-chain RPC | A restored hash is resolved against an unauthenticated third-party endpoint, which may not have the transaction, may serve a different history, or may refuse the request. |
| mount effect → wallet | An effect that could send a transaction or open a prompt turns a page reload into a signature request. This boundary is closed by construction, not by care. |
