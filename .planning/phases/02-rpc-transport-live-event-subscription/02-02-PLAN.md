<objective>
Build the one piece of machinery both hooks in this phase depend on and neither should own: a
non-React engine that seeds from a bounded scan, opens a live subscription, keeps a dense heartbeat,
watches for staleness, and degrades to HTTP polling — reporting every transition as an explicit
transport mode.

Purpose: LIVE-05 and LIVE-06 are the subtlest requirements in the phase. `fallback()`'s retry logic
genuinely does not cover the subscription code path, and viem's WebSocket transport can sit silently
closed with no error surfaced (`wevm/viem#2325`), so the degrade must be hand-built and the watchdog
is load-bearing rather than defensive. Implementing that twice — once in each hook — means two
chances to get it wrong and two places to fix it. Extracting it here also makes it testable against
a fake client, which is the only way LIVE-04's ordering guarantee and LIVE-05's degrade become
automated assertions instead of manual observations.

Output: `ui/src/lib/live-watch.ts` and `ui/src/lib/live-watch.test.ts`.
</objective>

<decisions_recorded>
- **D-06 is the degrade and recovery policy this engine implements.** The two milestone research
  documents appeared to disagree — STACK.md wanted a reconciliation pass running "regardless of
  subscription state", PITFALLS.md warned against running the poll "permanently in parallel" with a
  healthy subscription. They were describing different cadences. This engine runs the **slow**
  (60 s) reconciliation always, and reserves the **fast** (6 s) poll exclusively for confirmed-
  unhealthy mode. The slow pass is safe by construction because all state is merged by `messageId`
  rather than appended, so any overlap is absorbed by dedupe.
- **Degrade is terminal for the lifetime of the handle.** D-06 settles the cadences but not whether
  a degraded watch should periodically retry the WebSocket upgrade. It does not, for three reasons:
  `webSocket()` has already exhausted its own bounded reconnect (5 attempts) by the time the engine
  degrades, so an application-level retry would stack a second reconnect mechanism on top of viem's;
  an unbounded retry loop against a shared no-key public endpoint is the denial-of-service risk this
  phase's threat model names; and HTTP polling is the always-correct path for this project, so
  staying on it costs latency and nothing else. A remount or page reload retries naturally.
  *Reversibility: reversible — re-enabling an upgrade retry is a change inside this one function
  behind an unchanged handle interface.*
- **The heartbeat is `watchBlocks`, not the bridge event stream.** RESEARCH.md's design correction is
  binding: `BridgeTxInitiated` / `BridgeFinalized` are sparse, so "seconds since the last bridge event"
  cannot distinguish a healthy idle connection from a dead one. A per-block signal can.
</decisions_recorded>

    - `export interface LiveWatchHandle { stop: () => void }`
    - `export interface LiveWatchTiming { stalenessThresholdMs?: number; watchdogCheckIntervalMs?: number; reconcileIntervalMs?: number; fastPollIntervalMs?: number }` — every field optional, each defaulting to the derived or configured value. These overrides exist so the tests can drive the watchdog in tens of milliseconds instead of tens of seconds; they are not a second configuration surface and production callers pass none of them.
    - `export interface LiveWatchOptions { client, chainId, address, events, args?, webSocketEnabled, seed, onLogs, onTransportMode, onError?, timing? }` where `client` is the viem public client, `chainId` is REQUIRED and explicit, `address` is the bridge contract address, `events` is a readonly array of ABI event fragments to watch, `args` is the optional indexed-argument filter (used by plan 02-03 to scope a watch to one `messageId`), `webSocketEnabled` is a boolean the caller derives from `isWebSocketEnabled`, `seed` is an async function performing the bounded scan, `onLogs` receives each delivered batch, `onTransportMode` receives every mode transition, and `onError` is optional error reporting.
    - `createLiveWatch(options): LiveWatchHandle`

    Implement in this order, and make the order observable:

    1. Derive the effective timings: `stalenessThresholdMs` from `stalenessThresholdMs({ blockTimeMs: blockTimeMsForChain({ chainId }) })`, `watchdogCheckIntervalMs` from `WATCHDOG_CHECK_INTERVAL_MS`, `reconcileIntervalMs` from `scanConfiguration.reconcileInterval`, and the fast poll cadence from the existing 6-second field on `scanConfiguration` — with any `timing` override winning. Report the initial mode: `'reconnecting'` when `webSocketEnabled`, otherwise `'polling-fallback'`.
    2. Hold module-free local state in closure variables: a `stopped` flag, the current unwatch handles, `lastHeartbeatAt`, a `degraded` flag, and the two timer ids.
    3. **Seed before subscribe (LIVE-04).** `await seed()` fully, then — and only then, and only if `stopped` is still false — open the watchers. This ordering is the whole requirement: it must be an `await`, not a fire-and-forget, and there must be exactly one place in the function where `watchContractEvent` is first reached.
    4. Open the event watcher(s) via `client.watchContractEvent` for each fragment in `events`, passing `address`, `args` when provided, `onLogs`, and an `onError` that routes into the degrade path. When `webSocketEnabled`, do NOT pass `poll` at all — leave viem's index-0 introspection to choose the subscription path, per the explicit "don't hand-roll transport detection" guidance. When it is false, pass `poll: true` with the fast cadence and skip steps 5 and 6 entirely.
    5. **Heartbeat.** Open `client.watchBlocks({ onBlock, onError })`. `onBlock` sets `lastHeartbeatAt` to now and, on the first block, reports `'connected'`. Its `onError` routes into the degrade path. This watcher exists for one reason: to produce a dense signal, because bridge events are too sparse to distinguish idle from dead.
    6. **Watchdog.** `setInterval` at the check cadence: if `Date.now() - lastHeartbeatAt` exceeds the threshold and the handle is neither stopped nor already degraded, report `'stale'` and then run the degrade path. Guard on the `degraded` flag so the watchdog cannot fire twice — an ungated watchdog turns one dead socket into a teardown-and-reopen loop against a shared public endpoint.
    7. **Reconciliation.** `setInterval` at the reconcile cadence calling `seed()` and swallowing its rejection into the optional `onError`. This timer runs for the whole lifetime of the handle regardless of subscription health, per D-06, and is safe because callers merge by `messageId`.
    8. **The degrade path**, as one internal function: return immediately if `stopped` or `degraded`; set `degraded`; call every WebSocket-path unwatch (event watchers and heartbeat) and clear the watchdog timer; re-open the event watcher(s) with `poll: true` and the fast cadence; report `'polling-fallback'`. Do not schedule any WebSocket re-upgrade attempt — record in a one-line comment that viem's own bounded reconnect has already been exhausted at this point and that a remount is the retry mechanism.
    9. **`stop()`** sets `stopped`, calls every unwatch collected so far, and clears both timers — one function tearing down all four resources, which is the convention that survives a StrictMode double-mount. Make it idempotent, and make every callback (heartbeat, error, watchdog tick, reconcile tick) return early when `stopped` is set, so a callback that lands after teardown cannot resurrect a watcher.

    Use object parameters throughout and explicit return types on the exported function, matching
    `scanChain({ client, bridgeAddress, chainId })` and `pollWatcher({ ... })`. Reuse the
    `getErrorMessage({ error })` shape from `relayer/src/watcher.ts` for turning unknown throwables
    into strings rather than inventing another.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → third-party public RPC endpoint | Every log batch, block header and error this engine reacts to originates from unauthenticated public infrastructure outside the project's control. |
| engine → injected client | `createLiveWatch` acts on whatever client it is handed; a caller passing a client for the wrong chain would have this engine faithfully watch the wrong chain. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06 | Spoofing | `createLiveWatch({ client, chainId, ... })` | high | mitigate | The watched chain must never be inferable. `chainId` is a required option, is used only to derive the staleness threshold, and is never resolved from the client, from wallet state or from a default. Callers obtain the matching client from `getLiveClient({ chainId })`, which throws on an unknown chainId. Verified by the criterion that no wagmi wallet hook appears in this file. |
| T-02-07 | Denial of service | the degrade path and the watchdog interval | medium | mitigate | An ungated degrade turns one dead socket into a repeating teardown-and-reopen cycle against a shared no-key endpoint. A `degraded` flag guards the watchdog, the error path and the degrade function itself; degrade is terminal for the handle and schedules no WebSocket re-upgrade; and the exact-call-count test in Task 2 is what proves the bound rather than asserting it. The reconciliation cadence is 60 s, ten times slower than the poll it replaces as the default. |
| T-02-08 | Tampering | `onLogs` batches forwarded to callers | medium | mitigate | This engine does not interpret log contents; it forwards batches unchanged to the caller's `onLogs`, which routes them through `applyLogsByMessageId` from plan 02-01 where `removed: true` rollback and messageId dedupe are applied. Keeping interpretation out of the engine means there is exactly one place a fabricated or retracted log is handled, rather than two divergent ones. |
| T-02-09 | Repudiation | transport-mode reporting | medium | mitigate | A mode that silently claims health would make a stalled UI indistinguishable from a live one — the milestone's core failure mode. The engine reports `'connected'` only after an actual heartbeat block arrives, never at construction, and the initial state is `'reconnecting'`. The prohibition in `must_haves` states this as a must-NOT and Task 2 asserts the pre-heartbeat mode. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | accept | No new packages. This plan adds two files that import only `viem` types and existing project modules; RESEARCH.md's `## Package Legitimacy Audit` records "not applicable — no new packages" for the phase. No `[ASSUMED]`/`[SUS]` package, so no blocking legitimacy checkpoint. |
